Chapter 0

你现在在干什么

一句话：不看原码，自己写出一个能通过官方测试的 Agent 框架。

前面四周你写了检索、循环刹车、评测、命令行入口——都是零散零件。现在把它们换成一套真正的工程骨架：一个别人也在用的开源框架。

打个比方。学做菜有两种学法：看菜谱抄一遍，或者把大厨的招牌菜端上来，先尝，再自己复现，最后和他那盘对比。
复刻走的是第二条：测试就是那张"标准味道"的评分表，你做出来一尝就知道差在哪。

0.1为什么是它

条件swarm 的情况
代码量能吃下423 行，三个文件，一天能读完
不要 API key自带 tests/mock_client.py，模型是假的
有标准答案6 个官方测试，红了就是错了
有真实用法8 个示例应用：分流客服、天气助手、航空公司

0.2复刻的判定标准

不是"我读懂了"，也不是"能跑起来"。只有一条：

把原仓库的 swarm/core.py 挪走，用你自己的实现，让 pytest tests 全绿。测试是 OpenAI 写的，不是为你放宽过的。

全绿之后，你手上这个东西和官方版本行为等价。这就叫复刻成功。

别做的事。把原码复制过来改几个变量名，或者一边看一边抄。那样测试也会绿，但你只是在打字。正确姿势：读完一块，关掉窗口，凭记忆写。

Chapter 2

三个文件各自管什么

先认清职责，再动手。三个文件加起来 423 行。

2.1types.py —— 三个"表格"

42 行，只做一件事：定义三个数据类。它们不是逻辑，是"装东西的盒子"。

类字段是什么
Agentname / model / instructions / functions / tool_choice / parallel_tool_calls一个"角色"：叫什么、用哪个模型、说什么话、能用哪些工具
Responsemessages / agent / context_variables一次运行的产物：这轮说了什么、最后由谁接待、共享变量
Resultvalue / agent / context_variables工具函数可以返回的东西：一句话、换个人接待、或改共享变量

它们都继承 BaseModel（来自 pydantic）。作用：字段有默认值、能自动校验、能转成 JSON。

2.2util.py —— 把函数翻译成说明书

88 行，主力只有一个函数 function_to_json(func)。

模型看不懂 Python 函数，只能看 JSON 说明书。这个函数做的事：读函数的名字、docstring、参数名和类型注解，翻译成模型能读的 schema。

翻译结果长这样
{
  "type": "function",
  "function": {
    "name": "basic_function",
    "description": "",
    "parameters": {
      "type": "object",
      "properties": {
        "arg1": {"type": "string"},
        "arg2": {"type": "string"}
      },
      "required": ["arg1", "arg2"]
    }
  }
}

类型映射是死的：int → integer、str → string、float → number、bool → boolean。不写注解就当 string。

还有 debug_print：调试开关打开时才打印，平时闭嘴。

2.3core.py —— 主循环

293 行，六个部分：

行名字干什么
26class Swarm整个框架
27__init__存一个模型客户端；不给就新建官方客户端
32get_chat_completion拼 system 指令 + 历史 + 工具说明书，发请求
71handle_function_result把工具返回值统一成 Result
89handle_tool_calls执行模型点名的工具，把结果写成 role=tool 消息
139run_and_stream流式版本（先跳过）
231run主循环：问模型 → 有工具就执行 → 再问 → 直到没有工具

2.4run() 的六步骨架

这是整个框架的心脏。先看骨架，别急着写：

伪代码（不是最终代码）
1. 如果要求流式，转给 run_and_stream
2. 记下起点：active_agent、history、init_len
3. while 轮数还没超 max_turns 且还有 active_agent：
4.     问模型要一次回答
5.     把回答塞进 history
6.     如果回答里没有 tool_calls，或用户说别执行工具 → 结束
7.     执行工具，拿回 消息 / 共享变量 / 新 agent
8.     把消息并进 history，更新变量，必要时换 active_agent
9. 返回 Response（只返回这轮新增的消息）

读的时候盯住两个细节：init_len 为什么要减掉；active_agent 为什么可以被换掉。这两处就是"多 Agent"的全部秘密。

Chapter 3

六关：一关一个测试

每关只有一个目标：让对应测试变绿。不贪多。

关目标变绿的测试改哪
v0.1三个数据类写出来import 不再报错types.py
v0.2函数 → JSON 说明书test_basic_function、test_complex_functionutil.py
v0.3单轮问答能返回test_run_with_simple_messagecore.py 的 run + get_chat_completion
v0.4模型要求调工具时能执行test_tool_callcore.py 的 handle_tool_calls
v0.5关闭工具执行也能正常返回test_execute_tools_falsecore.py 里 execute_tools 的判断
v0.6工具返回 Agent 时换人接待test_handoffcore.py 里 active_agent 的更新

3.1v0.1 只写三个类

这一关不写任何逻辑。照着第 2 章的字段表，在 my-swarm\swarm\types.py 里定义三个类，字段名、默认值都要和官方一致。

另外 __init__.py 要把这三个类和 Swarm 导出，因为测试是 from swarm import Swarm, Agent。

验收：pytest tests -q 的报错从 ImportError 变成 AttributeError 或 ImportError: Swarm。这说明 types 已经过了，轮到 core。

3.2v0.2 最难的是"类型映射"

这一关有现成的标准答案——测试里写死了期望的 JSON。test_basic_function 要求不写注解的参数当 string；test_complex_function 要求四种类型各自对上，而且有默认值的参数不进 required。

要用到的两样东西：inspect.signature(func) 拿参数表，func.__doc__ 拿描述。

最容易忘的一条：required 只放"没有默认值"的参数。arg3、arg4 有默认值，所以只出现 arg1、arg2。

3.3v0.3 只要一条消息能回来

这个测试最简单：给一句 "Hello"，断言最后一条消息的角色是 assistant、内容是假模型写死的那句。

你需要让 run 至少做到：调一次模型 → 把回答塞进 history → 没有工具就跳出循环 → 返回 Response。

3.4v0.4 工具调用的闭环

炮制顺序（模型视角）：

  1. 模型说"我要调 get_weather，参数是 {location: "San Francisco"}"
  2. 你按名字找到函数，json.loads 参数，调用它
  3. 把返回值包装成一条 {"role": "tool", "tool_call_id": ..., "content": ...}
  4. 这条消息放回 history，再问模型一次

测试断言的是：工具真的被调用了一次；调用时传进去的参数是对的；最后返回的消息里既有工具结果、也有模型的最终回复。

3.5v0.5 和 v0.6 只差两个判断

v0.5 是"用户说别执行工具"：execute_tools=False 时，即使模型给了 tool_calls 也不能执行，直接结束这一轮。

v0.6 是"换人接待"：工具函数返回的是一个 Agent 实例时，不要当字符串用，而是把它变成新的 active_agent，并给模型回一句 {"assistant": "新角色名"}。

打个比方。客服接了你的电话，发现是退款问题，说"我帮您转接售后"——这就是 handoff。转接之后，说话的人变了，但通话没断，历史还在。

Chapter 4

怎么读 pytest 的报错

报错不是惩罚，是提示。学会读它，卡住的时间能少一半。

一段真实的失败输出，分三段看：

失败输出（示意）
FAILED tests/test_util.py::test_basic_function - AssertionError: assert {...} == {...}
E       AssertionError: assert {'type': 'function', ...} == {'type': 'function', ...}
E         Omitting 1 identical items, use -vv to show
E         Differing items:
E         {'function': {...}} != {'function': {...}}
========================= 1 failed, 5 passed in 0.31s ========================
看哪它在说什么
第一行 FAILED ...::test_basic_function哪个测试挂了。名字就是范围，其它先不管
中间的 E 行期望值和你给的值哪里不一样。加 -vv 能看到完整差异
最后一行 1 failed, 5 passed进度条。passed 从 0 涨到 6，就是你的进度

4.1三种常见报错

报错含义先查什么
ImportError名字没定义或没导出函数名拼写、__init__.py 有没有导出
AttributeError对象身上没这个属性类字段名是不是和官方一致
AssertionError跑通了，但结果不对加 -vv 看完整差异，逐字段比
一个小技巧。先只跑一个测试：pytest tests/test_util.py::test_basic_function -vv。范围越小，报错越好读。

Chapter 5

三个必卡点

这三个地方，第一次写基本都会错。提前知道，能省两小时。

5.1required 列表

直觉是"把所有参数都放进 required"，但测试要求只放没默认值的。判断方法是看 param.default 是不是 inspect.Parameter.empty。

5.2工具结果必须回填

执行完工具后，如果不把结果以 role="tool" 的消息塞回 history，模型下一轮会以为"我还没查过"，于是再调一次——死循环。

而且每条工具消息都要带 tool_call_id，它对应模型那次调用的编号，模型靠它对账。

5.3返回值的三种类型

工具返回怎么办
普通字符串 / 数字转成字符串，包进 Result.value
Result 对象直接用，它可能带了 agent 和共享变量
Agent 对象当作"转接"，换成新的 active_agent
卡住超过 15 分钟就降级。第一级：看一眼原码对应函数的注释和返回类型。第二级：对照测试里的期望值反推结构。第三级：直接问我，说清"哪一行、报什么错"。

自测三问（读完这章就能答）：

1. 为什么 function_to_json 需要读函数的类型注解？

2. 工具执行完，为什么必须把结果写回 history？

3. handoff 之后，history 会被清空吗？

Chapter 6

术语表与进度表

手机上翻着看，把这几个词记牢就够用了。

词一句话
Agent一个角色：名字 + 模型 + 指令 + 可用工具
handoff转接：把当前接待人换成另一个 Agent，历史不断

max_turns最多循环几轮，防止无限调用
TDD先写失败的测试，再写实现让它变绿
