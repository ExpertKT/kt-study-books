Chapter 0

数据管线：读表格、算统计、存结果

学完能做出：把一份 CSV 变成一份随时能再读的 JSON 统计报告。

你有 10 天的学习记录，想知道两件事：一共学了多久；算法和 Python 哪个正确率更高。

打个比方。做饭分三步：买菜、洗菜是一步；切菜、配菜是第二步；装盘端出去是第三步。数据管线就是同一件事——读进来（买菜）、算一算（切配）、写出去（装盘）。少了任何一步，菜都上不了桌。

0.1第一步：读进来 B

CSV 就是“用逗号分隔的表格”，第一行是表头。Python 自带 csv，不用装库。

pipeline.py
import csv
from pathlib import Path

rows = []
with open("data/study.csv", encoding="utf-8", newline="") as file:
    for row in csv.DictReader(file):        # 每一行变成一个字典
        rows.append({
            "subject": row["科目"],          # 表头叫“科目”，就按这个名字取值
            "minutes": int(row["时长分钟"]),  # 表格里是文字，转成整数
            "accuracy": float(row["正确率"]), # 转成小数
        })

print(len(rows))
print(rows[0])
实际输出
10
{'subject': '算法', 'minutes': 45, 'accuracy': 0.8}

csv.DictReader 做的事：把表头当键，把每行当值，交给你一串字典。表格里的数字读进来仍然是文字，所以要 int()、float() 转一次。

0.2第二步：算一算 B

按科目分组，各算平均。分组的动作是“以科目为键，把同类行塞进同一个列表”。

pipeline.py（接着写）
by_subject = {}
for row in rows:
    by_subject.setdefault(row["subject"], []).append(row)

summary = {}
for name, group in by_subject.items():
    summary[name] = {
        "count": len(group),
        "avg_min": round(sum(r["minutes"] for r in group) / len(group), 1),
        "avg_acc": round(sum(r["accuracy"] for r in group) / len(group), 3),
    }

print(summary)
实际输出
{'算法': {'count': 5, 'avg_min': 36.0, 'avg_acc': 0.71}, 'Python': {'count': 5, 'avg_min': 50.0, 'avg_acc': 0.816}}

结果读法：算法练了 5 天、平均 36 分钟、平均正确率 0.710；Python 5 天、50 分钟、0.816。也就是说 Python 花的时间更长，正确率也更高。

0.3第三步：写出去 B

统计结果要留着下次用，写成一个 JSON 文件。JSON 就是“带引号的键值对文本”，几乎所有程序都能读。

pipeline.py（收尾）
import json

result = {"total_min": sum(r["minutes"] for r in rows), "subjects": summary}
Path("results").mkdir(exist_ok=True)
Path("results/summary.json").write_text(
    json.dumps(result, ensure_ascii=False, indent=2),
    encoding="utf-8",
)
print(result["total_min"])
实际输出
430

ensure_ascii=False 让中文原样写出，而不是变成 \u7b97\u6cd5；indent=2 让文件有缩进，人能直接读。

词人话
CSV逗号分隔的纯文本表格，第一行是表头
DictReader把每一行变成“表头 → 值”的字典
setdefault(k, [])键不存在就先放一个空列表，然后返回它
JSON一种人人都能读的键值对文本，用来存、用来传
dumps / loadsPython 对象 → 文本 / 文本 → Python 对象
三个常见错。不加 newline=""，Windows 上可能多出空行；忘记 int()，求和会变成字符串拼接；忘写 encoding="utf-8"，中文可能变乱码。

Chapter 1

向量与相似度：让程序判断“意思接近”

学完能做出：把三句话变成三条打分卡，算出谁和谁最像。

程序不认识“意思”。它只会算数。所以要让“意思接近”变成“数字接近”。

打个比方。给一道菜打三个分：辣、甜、咸，每项 0 到 5 分。宫保鸡丁是（辣 4，甜 2，咸 3），水煮鱼是（辣 5，甜 0，咸 4），蛋糕是（辣 0，甜 5，咸 0）。
两张打分卡越接近，菜的口味就越像。句子也能打这样的分：每个维度代表一类含义，分数越高，越沾这个意思。

1.1句子变成三个数 B

先手动给三句话打分，维度用“算法、练习、记忆”：

句子算法练习记忆
算法练习310
刷算法题220
背单词013

一行三个数，就叫一个向量。真实的大模型会用几百上千个维度，原理一样，只是数更多。

1.2怎么算“像” B

用余弦相似度：把两个向量当成两支箭，看它们指向是否一致。方向一致得 1，垂直得 0，相反得 -1。

similarity.py
import math

def cosine(a, b):
    dot = sum(x * y for x, y in zip(a, b))        # 对应位置相乘再相加
    na = math.sqrt(sum(x * x for x in a))         # 第一支箭的长度
    nb = math.sqrt(sum(y * y for y in b))         # 第二支箭的长度
    return dot / (na * nb)

vectors = {"算法练习": [3, 1, 0], "刷算法题": [2, 2, 0], "背单词": [0, 1, 3]}
base = vectors["算法练习"]
for name, vec in vectors.items():
    print(name, round(cosine(base, vec), 3))
实际输出
算法练习 1.0
刷算法题 0.894
背单词 0.1

自己和自己比是 1.0；“刷算法题”方向接近，0.894；“背单词”几乎垂直，0.1。程序据此就能排序：谁最像。

1.3这套东西用在哪 C

你以后会遇到“检索”：用户问一句话，从几百条资料里找最相关的几条。做法就是——每句话提前算好向量，存起来；提问时算提问的向量，逐个比余弦，取前几名。这就是 RAG（先检索、再让模型回答）的地基。

词人话
向量一串数，代表一个东西的特征
维度这串数有几个，就代表几个特征
点积对应位置相乘再相加，衡量“同方向的程度”
余弦相似度只看方向不看长短，范围 -1 到 1
注意。余弦只看方向，不看长度。所以“算法练习”和“算法练习算法练习”会被判成完全一样（1.0），尽管后者说了两遍。

自测三问：

1. 为什么不能直接用文字比较“像不像”？

2. 余弦相似度里，1、0、-1 各代表什么？

3. 检索时为什么要先给每句话算好向量？

练习

加一句“看算法讲解”（建议打分：算法 3，练习 0，记忆 1），算出它和“算法练习”的相似度，再排序输出前三名。

Chapter 2

拟合一条直线：机器怎么“学”

学完能做出：用 10 条记录，拟合出一条“学习时长 → 正确率”的直线，并预测新时长。

手上有 10 组“学了多久 / 正确率多少”。问题：能不能给一条规律——多学 10 分钟，正确率大概涨多少？

打个比方。桌上有 10 颗钉子，你要拉一根绳子，让它尽量贴着所有钉子。
绳子可能偏高、偏低、斜得太厉害。每颗钉子到绳子的距离，平方后加起来，越小说明贴得越好。这个“总距离”就叫损失。
调整绳子的办法像蒙眼下山：你只看脚下哪边更陡，就朝那边迈一小步；每一步都重复，直到走到谷底。这就是梯度下降。

2.1先把数据摆平 A

时长在 20 到 70 之间，正确率在 0.55 到 0.95 之间。两个数单位差得远，直接算会让“时长”压过“正确率”。所以先做标准化：减均值、除标准差，把两边都变成“离平均有几个身位”。

fit_line.py
import numpy as np

x = np.array([45, 30, 60, 25, 50, 40, 35, 55, 20, 70], dtype=float)
y = np.array([0.80, 0.70, 0.90, 0.60, 0.85, 0.75, 0.65, 0.95, 0.55, 0.88], dtype=float)

x_mean, x_std = x.mean(), x.std()
y_mean, y_std = y.mean(), y.std()
xs = (x - x_mean) / x_std            # 标准化后的时长
ys = (y - y_mean) / y_std            # 标准化后的正确率

标准化不改变规律，只是换了一把尺子。

2.2一根绳子 = 两个参数 A

直线写成 预测值 = w * 输入 + b。w 管倾斜，b 管上下平移。机器“学”，学的就是这两个数。

fit_line.py（训练）
w, b = 0.0, 0.0
lr = 0.1                                   # 学习率：每步迈多大
for step in range(200):
    pred = w * xs + b                      # 当前绳子的预测
    loss = ((pred - ys) ** 2).mean()       # 所有钉子到绳子的平均平方距离
    dw = 2 * ((pred - ys) * xs).mean()     # 往哪边调 w 更陡
    db = 2 * (pred - ys).mean()            # 往哪边调 b 更陡
    w -= lr * dw                           # 朝下坡方向迈一步
    b -= lr * db
    if step % 50 == 0:
        print(f"step {step:3d} loss {loss:.4f}")
实际输出
step   0 loss 1.0000
step  50 loss 0.1501
step 100 loss 0.1501
step 150 loss 0.1501

损失从 1.0000 掉到 0.1501，前 50 步就把能降的都降完了。剩下的 0.1501 是数据本身的抖动，直线贴不成完美。

2.3翻译回你熟悉的单位 A

fit_line.py（换算与预测）
slope = w * y_std / x_std
intercept = y_mean + y_std * b - slope * x_mean
print(f"正确率 ≈ {slope:.4f} * 时长 + {intercept:.3f}")
print(f"学 40 分钟，预测正确率 {slope * 40 + intercept:.2f}")
print(f"学 70 分钟，预测正确率 {slope * 70 + intercept:.2f}")
实际输出
最终 w=0.922 b=-0.000
正确率 ≈ 0.0078 * 时长 + 0.428
学 40 分钟，预测正确率 0.74
学 70 分钟，预测正确率 0.97

结论：每多学 10 分钟，正确率约涨 0.078；学 40 分钟大概 0.74，学 70 分钟大概 0.97。注意 0.97 已经贴近上限，真实世界不会一直线性涨——这就是“模型有适用范围”。

词人话
参数 w、b直线要学的两个数：倾斜、平移
损失 loss预测和真实差多少，平方后取平均
梯度“往哪个方向调，损失降得最快”
学习率 lr每步迈多大。太大冲过头，太小走太慢
标准化减均值除标准差，让不同单位的数可比
两个坑。学习率过大，loss 会变成 nan 或来回震荡；忘了标准化，w 会小得看不见，误以为“没学到东西”。

自测三问：

1. 直线里的 w 和 b 各控制什么？

2. loss 从 1.0 降到 0.15，说明绳子发生了什么变化？

3. 为什么预测 70 分钟的结果不一定可信？

练习

把学习率从 0.1 改成 1.0，跑一次，观察 loss 是否还稳定下降；再改成 0.01，数一数要不要更多步才降下去。

Chapter 3

分类：画一条线，猜对多少

学完能做出：只给学习时长，判断“这次能不能及格”，并算出猜对的比例。

上一章预测的是一个具体数值。这一章要的是“是 / 否”：这次学习能不能及格。

打个比方。门口站着一位保安，手里有一条线：站在线左边的不让进，右边的放行。
我们要学的是“这条线画在哪”。学完之后，来一个人，看他在线的哪边，就给出判断。
判断对不对，要拿没参与画线的人去试——就像练习题用来学，考试题用来验。

3.1先定“及格”是什么 A

正确率 ≥ 0.7 记 1（及格），否则记 0。这样“数值预测”就变成了“是 / 否”。

classify.py
import numpy as np

minutes = np.array([45, 30, 60, 25, 50, 40, 35, 55, 20, 70], dtype=float)
passed = np.array([1, 1, 1, 0, 1, 1, 0, 1, 0, 1], dtype=float)

x_mean, x_std = minutes.mean(), minutes.std()
xs = (minutes - x_mean) / x_std


def sigmoid(z):
    return 1 / (1 + np.exp(-z))      # 把任意数压到 0~1，当作概率

sigmoid 的作用：原始输出可能是 -3 或 +5，压到 0 到 1 之间，才能当概率读。

3.2画线：训练 A

classify.py（训练）
def train(xs, ys, lr=0.5, steps=300):
    w, b = 0.0, 0.0
    for _ in range(steps):
        p = sigmoid(w * xs + b)          # 当前判断“及格”的概率
        dw = ((p - ys) * xs).mean()      # 预测偏乐观还是偏悲观，往反方向调
        db = (p - ys).mean()
        w -= lr * dw
        b -= lr * db
    return w, b

和上一章的梯度下降同一个套路，只是把“平方误差”换成了“概率误差”。

3.3练习题与考试题 A

classify.py（划分与评估）
train_mask = np.array([True]*7 + [False]*3)   # 前 7 条用来学
test_mask = ~train_mask                        # 后 3 条用来验

w, b = train(xs[train_mask], passed[train_mask])

def predict(w, b, values):
    p = sigmoid(w * values + b)
    return (p >= 0.5).astype(int), p           # 概率过半就判及格

pred_train, _ = predict(w, b, xs[train_mask])
pred_test, prob_test = predict(w, b, xs[test_mask])
print(f"训练集准确率 {(pred_train == passed[train_mask]).mean():.0%}")
print(f"测试集准确率 {(pred_test == passed[test_mask]).mean():.0%}")
for m, p, t in zip(minutes[test_mask], prob_test, passed[test_mask]):
    print(f"时长 {m:.0f} → 概率 {p:.2f}，预测 {int(p >= 0.5)}，真实 {int(t)}")
print(f"分界线约在 {x_mean + (-b / w) * x_std:.1f} 分钟")
实际输出
训练集 7 条，准确率 71%
测试集 3 条，准确率 100%
时长 55 → 概率 0.99，预测 1，真实 1
时长 20 → 概率 0.07，预测 0，真实 0
时长 70 → 概率 1.00，预测 1，真实 1
分界线约在 32.1 分钟

测试集 3 条全对，不代表模型好——样本太少。真正评估要几十上百条，还要看“错的那类错得多不多”。

换个说法理解“过拟合”。把练习题背得滚瓜烂熟，连题号都记住，考试一换题就傻眼。模型也一样：在训练集上 100%，测试集上掉到 60%，就是背题了。
词人话
分类输出是“哪一类”，不是具体数值
概率 / 阈值模型给 0~1 的分，超过 0.5 就判“是”
训练集 / 测试集用来学的数据 / 用来验的数据，不能混
准确率猜对的比例
过拟合训练集很好、测试集很差，等于背题

自测三问：

1. 为什么不能拿训练集的数据来报准确率？

2. 概率 0.99 和 1.00 有什么区别？

3. 测试集只有 3 条时，100% 意味着什么？

练习

把及格线从 0.7 改成 0.8，重新算标签，再训练一次。观察分界线往哪边移、测试集还对不对。

Chapter 4

调用 LLM：你在点外卖

学完能做出：写一个本机模拟模型服务，再用 HTTP 向它提问、拿到回复。

模型不在你电脑上，在别人的服务器上。你的程序要做的，是把问题送过去，再把答案取回来。

打个比方。点外卖：你在 App 里写“一份牛肉面，不要香菜”（这就是 prompt），平台把订单传给商家（HTTP 请求），商家做完打包送回（JSON 响应）。
你不需要知道厨房在哪、灶多大，只要会写订单、会收餐。调模型就是点外卖。

4.1先在家开个“假厨房” A

没有 key 也能练。用标准库起一个本机服务，收到问题就按规则回一句。

mock_llm.py
import json, threading
from http.server import BaseHTTPRequestHandler, HTTPServer

class Handler(BaseHTTPRequestHandler):
    def do_POST(self):
        length = int(self.headers["Content-Length"])
        body = json.loads(self.rfile.read(length))
        prompt = body["prompt"]
        if "时长" in prompt:
            reply = "建议每天 40 分钟：先做题，再看讲解。"
        else:
            reply = "收到你的问题：" + prompt[:20]
        data = json.dumps({"reply": reply}, ensure_ascii=False).encode("utf-8")
        self.send_response(200)
        self.send_header("Content-Type", "application/json; charset=utf-8")
        self.send_header("Content-Length", str(len(data)))
        self.end_headers()
        self.wfile.write(data)

    def log_message(self, *args):
        pass

server = HTTPServer(("127.0.0.1", 18090), Handler)
threading.Thread(target=server.serve_forever, daemon=True).start()

4.2下单与收餐 A

mock_llm.py（接着写）
import urllib.request

def ask(prompt):
    request = urllib.request.Request(
        "http://127.0.0.1:18090/chat",                     # 厨房地址
        data=json.dumps({"prompt": prompt}, ensure_ascii=False).encode("utf-8"),
        headers={"Content-Type": "application/json"},      # 告诉对方：我送的是 JSON
    )
    with urllib.request.urlopen(request, timeout=3) as response:
        return json.loads(response.read())["reply"]

print(ask("我每天学习时长多少合适？"))
server.shutdown()
实际输出
建议每天 40 分钟：先做题，再看讲解。

4.3换成真实接口要改哪三处 B

位置模拟版真实版
地址127.0.0.1:18090/chat服务商给的 base_url，如 /v1/chat/completions
请求体{"prompt": ...}{"model": ..., "messages": [{"role":"user","content":...}]}
认证不需要请求头加 Authorization: Bearer sk-...

其余不变：还是 POST、还是 JSON、还是从响应里取文本。模拟服务的价值就在这里——协议学会了，换地址和字段就能接真模型。

词人话
API别人开给你的一扇门，按约定递东西进去
endpoint这扇门的具体地址（URL）
prompt你写的那张订单
JSON双方都认的文本格式
token模型计费的最小单位，约等于半个汉字到一个词
三个坑。忘了 Content-Type: application/json，服务端解析不了；timeout 不写，卡住就没完；把 key 写进代码再传仓库，等于公开密码。

Chapter 5

结构化输出：让它交表格，不是作文

学完能做出：要求模型返回 JSON，解析失败时自动重问一次，并把字段直接用起来。

模型回你一段话，人能读，程序不能。程序要的是字段：科目是什么、时长是多少。

打个比方。你让同事“把这单记下来”，他回你一段流水账，你还得自己抄进表格。
换个说法：“请按表格填：科目、时长。”他就交回一张填好的表。结构化输出就是要求对方交表，而不是交作文。

5.1自由发挥 vs 交表格 A

先看自由发挥的后果：返回的是一句话，json.loads 直接失败。

structured.py
import json

def fake_model(prompt, strict=False):
    if strict:
        return '{"subject": "算法", "minutes": 45}'
    return "我猜是算法，45 分钟吧"

text = fake_model("帮我提取：今天做了 45 分钟算法")
print(text)
json.loads(text)          # 这一行会抛 JSONDecodeError
实际输出
我猜是算法，45 分钟吧
json.decoder.JSONDecodeError: Expecting value: line 1 column 1 (char 0)

5.2加一句“只输出 JSON”，失败就重试 A

重试不是碰运气，而是把要求说得更死。真实调用时还可以降低随机性（temperature 设 0）。

structured.py（完整）
def extract(prompt):
    text = fake_model(prompt)
    try:
        return json.loads(text), text
    except json.JSONDecodeError:
        strict_prompt = prompt + "\n只输出 JSON，不要解释。"
        text2 = fake_model(strict_prompt, strict=True)
        return json.loads(text2), text2

result, raw = extract("帮我从这句话里提取：今天做了 45 分钟算法")
print("第二次返回：", raw)
print("取用字段：科目 =", result["subject"], "，时长 =", result["minutes"])
实际输出
第一次返回：我猜是算法，45 分钟吧
解析失败，加一句“只输出 JSON”再问
第二次返回： {"subject": "算法", "minutes": 45}
解析成功： {'subject': '算法', 'minutes': 45}
取用字段：科目 = 算法 ，时长 = 45

5.3字段到手之后 B

拿到 result 就等于拿到一个普通字典，可以写进 CSV、存进 sqlite、拿去算统计。模型输出不再是一段只能看的文字，而是一行能用的数据。

约定：字段名固定成 subject、minutes，并要求“只输出 JSON”。字段名一旦定下，程序就能稳定解析；让模型自由命名，接一次崩一次。
词人话
结构化输出让模型按固定字段返回，而不是自由文字
schema字段清单：叫什么、什么类型、必不必填
解析把文本变成程序能用的对象
重试失败后用更严格的要求再问一次，而不是原样重发
两个坑。模型爱在 JSON 外面包一句“好的，这是结果：”，所以解析前可能要截取第一个 { 到最后一个 }；重试没有上限，写死最多 2 次，避免死循环烧钱。

Chapter 6

最小 Agent：想一步、做一步、看结果

学完能做出：一个能自己决定“先查天气、再决定带不带伞”的循环程序，并把每一步写进日志。

单次问答解决不了多步任务。“明天要不要带伞”要先查天气，再根据天气给建议。两步之间要有人做决定。

打个比方。带一个实习生干活。你不能一口气说完所有步骤，只能说“你先去查天气”“根据结果再决定”。
他会：想一下该干什么 → 去做 → 看结果 → 再想下一步，直到事情办完。为防止他钻牛角尖，你规定“最多五步，走完就停”。
这个循环，就是 Agent。

6.1先给它几件工具 A

工具就是普通函数：收参数、给结果。名字、参数、返回值都要写清楚，模型才知道什么时候该用哪个。

agent.py
def get_weather(args):
    return {"city": args["city"], "rain": True}

def plan_trip(args):
    return "带伞" if args["rain"] else "不用带伞"

TOOLS = {"get_weather": get_weather, "plan_trip": plan_trip}

6.2循环：想、做、看 A

agent.py（循环）
import json, sqlite3

state = {"city": "常州", "rain": None, "advice": None}
db = sqlite3.connect(":memory:")
db.execute("CREATE TABLE steps (step INTEGER, action TEXT, result TEXT)")

for step in range(1, 6):                      # 最多五步
    if state["rain"] is None:
        action, args = "get_weather", {"city": state["city"]}
    elif state["advice"] is None:
        action, args = "plan_trip", {"rain": state["rain"]}
    else:
        break                                  # 事情办完，退出

    result = TOOLS[action](args)               # 真正动手
    if action == "get_weather":
        state["rain"] = result["rain"]          # 把结果记进状态
    else:
        state["advice"] = result

    print(f"[{step}] 调工具 {action}({json.dumps(args, ensure_ascii=False)}) → {json.dumps(result, ensure_ascii=False)}")
    db.execute("INSERT INTO steps VALUES (?, ?, ?)", (step, action, json.dumps(result, ensure_ascii=False)))

db.commit()
answer = f"明天{state['city']}有雨，出门{state['advice']}"
print(f"[{step}] 结束：{answer}")
print("日志：", db.execute("SELECT step, action FROM steps").fetchall())
实际输出
[1] 调工具 get_weather({"city": "常州"}) → {"city": "常州", "rain": true}
[2] 调工具 plan_trip({"rain": true}) → "带伞"
[3] 结束：明天常州有雨，出门带伞
日志： [(1, 'get_weather'), (2, 'plan_trip')]

关键在 state：它记住“天气查过没有、建议给过没有”。没有状态，循环就会一直重复查天气，永远停不下来。

flowchart TD
    A["开始：目标"] --> B["看状态：还缺什么"]
    B --> C{"有下一步？"}
    C -->|"有"| D["调工具，拿到结果"]
    D --> E["把结果写进状态"]
    E --> B
    C -->|"没有"| F["输出答案"]
    B --> G{"超过最大步数？"}
    G -->|"是"| H["停止，报告未完成"]

看图要点：循环的出口有两个——事情办完，或者步数用尽。

6.3模型真的会选工具 A

6.2 里的 decide() 是写死的规则。真实协议里，是模型返回一个工具调用，你的程序解析、执行、再把结果喂回去。

tool_call_demo.py
def model(messages):
    if len(messages) == 1:
        return {"tool_call": {"name": "get_weather", "arguments": {"city": "常州"}}}
    return {"content": "明天常州有雨，带伞。"}

messages = [{"role": "user", "content": "明天要不要带伞？"}]
for step in range(1, 4):
    reply = model(messages)
    if "tool_call" in reply:
        call = reply["tool_call"]
        print(f"[{step}] 模型要求调用 {call['name']}(...)")
        result = TOOLS[call["name"]](call["arguments"])
        messages.append({"role": "assistant", "content": json.dumps(reply, ensure_ascii=False)})
        messages.append({"role": "tool", "name": call["name"], "content": json.dumps(result, ensure_ascii=False)})
    else:
        print(f"[{step}] 模型最终回答：{reply['content']}")
        break
实际输出
[1] 模型要求调用 get_weather({"city": "常州"})
[2] 模型最终回答：明天常州有雨，带伞。

和 6.2 的区别：动作不是代码里判定的，而是模型返回的；程序只负责执行和白名单校验。接真实接口时，这个结构对应 tool_calls 字段，流程一模一样。

角色消息内容
user问题
assistant要求调用某个工具，带参数
tool工具的真实返回值，按名字对应
两个坑。把模型给的工具名直接当函数名调用，等于把门钥匙交给它；工具结果不写回消息列表，模型下一轮就“忘了自己查过什么”。

1. 6.2 和 6.3 的动作分别由谁决定？

2. 工具结果以哪种 role 写回？

3. 为什么工具名必须过白名单？

6.4为什么一定要日志 B

Agent 出错时，你看到的只是“答得不对”。要知道哪一步开始错，只能靠日志：调了哪个工具、参数是什么、回了什么、第几步。写进 sqlite，事后能查。

agent.py（日志）
import sqlite3
db = sqlite3.connect(":memory:")
db.execute("CREATE TABLE steps (step INTEGER, action TEXT, result TEXT)")
db.execute("INSERT INTO steps VALUES (?, ?, ?)", (step, action, str(result)))
db.commit()
print(db.execute("SELECT step, action FROM steps").fetchall())
词人话
工具一个普通函数，参数和返回值说清楚
状态 state记住“做到哪一步了”的小本子
循环上限最多走几步，防止绕圈烧钱
日志每步的输入输出，出错时唯一的证据
两个坑。没有上限，模型可能反复调同一个工具；没有日志，只能看到最终答案，无法定位是哪一步开始错。

自测三问：

1. 这个循环靠什么判断“可以停了”？

2. 如果去掉 max_steps，可能发生什么？

3. 日志里应该记哪三样东西？

评测与成本：改完到底变好没有

学完能做出：10 条测试问题，算出通过率，并粗估这次改动的 token 成本。

改了 prompt、换了模型，感觉“好像好一点”。感觉不算数，要有一份固定的卷子，每次跑同一套题。

7.1卷子和评分标准 B

CASES = [

评分标准故意写得简单：回复里必须出现某个关键词。关键词写得太宽，什么都能过；写得太窄，正确回答也会被判错。这一条本身就是需要打磨的地方。

测试集固定的一批问题和预期答案
通过率答对的比例，用来横向比较版本
token计费单位，输入输出都算
