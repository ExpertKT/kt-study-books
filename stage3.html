Chapter 0

从脚本到工程：配置、日志、入口

学完能做出：一个带配置文件、会写日志、有明确入口的程序骨架。

阶段二的代码，参数都写死在函数里。改个城市要改代码，出了错没有任何记录。这一章先解决这两件事。

打个比方。开一家小店，三样东西缺一不可：菜单（客人能选什么，你不用每次口头解释）、账本（谁来过、点了什么、出了什么问题）、店门（客人从哪进来）。
配置文件是菜单，日志是账本，入口脚本是店门。没有它们，那不叫店，叫你自己在家做饭。

0.1菜单：config.json A

config.json
{
  "city": "常州",
  "max_steps": 5,
  "retry_limit": 2,
  "model_url": "http://127.0.0.1:18090/chat"
}

四个值都是“会变但不想改代码”的东西。改城市、改步数上限、换模型地址，只动这一个文件。

0.2账本：日志 A

config_and_log.py
import json, logging

logging.basicConfig(
    level=logging.INFO,

实际输出

Chapter 1

工具层：签名、校验、重试

学完能做出：一个失败会自动重试、失败两次就如实报错的工具调用层。

真实工具会超时、会返回奇怪的参数、会突然挂掉。工具层就是给这些意外加一层缓冲。

打个比方。插头要有统一的规格（参数校验），不然插不进去；跳闸了要能自动合闸（重试），合两次还跳，就得停电检修（报错），不能一直合闸把线路烧了。

1.1先看失败长什么样 A

tools.py
CALLS = {"n": 0}

def flaky_weather(args):
    CALLS["n"] += 1
    if CALLS["n"] < 3:
        raise TimeoutError("weather service timeout")
    return {"city": args["city"], "rain": True}

这个工具前两次必失败，第三次成功。用它才能验证重试是真的有用。

1.2重试不是循环重发 A

tools.py（调用层）
def call_tool(name, args, retry_limit=2):
    for attempt in range(1, retry_limit + 2):      # 首次 + 2 次重试
        try:
            result = TOOLS[name](args)
            return {"ok": True, "result": result, "attempts": attempt}
        except Exception as error:
            print(f"  第 {attempt} 次失败：{type(error).__name__}: {error}")
            if attempt > retry_limit:
                return {"ok": False, "error": str(error), "attempts": attempt}
实际输出
  第 1 次失败：TimeoutError: weather service timeout
  第 2 次失败：TimeoutError: weather service timeout
{'ok': True, 'result': {'city': '常州', 'rain': True}, 'attempts': 3}

三个要点：返回值永远是一个字典（成功失败结构一致）；记下第几次才成功；超过上限就停下，不无限重试。

flowchart TD
    A["调用工具"] --> B{"成功？"}
    B -->|"是"| C["返回 ok 与结果"]
    B -->|"否"| D{"还有重试次数？"}
    D -->|"有"| E["等一会儿再试"]
    E --> A
    D -->|"没有"| F["返回 error 与原因"]

看图要点：只有“没到上限”才回到调用，到了上限就如实报错，不再绕圈。

1.3参数校验放在工具入口 B

模型可能传错东西：把城市传成数字、少传字段。校验放在工具内部，用一句明确的话拒绝，比在后面崩掉好排查。

tools.py（校验）
def get_weather(args):
    city = args.get("city")
    if not isinstance(city, str) or not city:
        raise ValueError("city 必须是非空字符串")
    return {"city": city, "rain": True}
词人话
重试次数“再多试几次”，不含第一次
幂等同一个请求做两遍，结果一样；只有幂等的工具才适合自动重试
返回值统一成功失败都是字典，调用方不用猜
校验进门先查证件，别等用到一半才崩
两个坑。把“发消息”“下单”这类工具自动重试，可能发两遍；重试之间没有等待，对方可能还没恢复。

1. retry_limit=2 一共会尝试几次？

2. 为什么工具返回要统一成字典？

3. 哪些工具不能自动重试？

Chapter 2

接模型：messages 协议与用量

学完能做出：用主流消息格式调用模型，并读出这次花了多少 token。

阶段二用的是自定义的 {"prompt": ...}。真实接口不是这样，它要一串“谁说了什么”。

打个比方。你跟客服聊天，系统会显示“客服：您好”“你：我想退货”“客服：请提供订单号”。
模型收到的也是这种带角色的对话记录，不是一句孤立的问题。角色只有三种：system（规定它怎么说话）、user（你说的）、assistant（它说的）。

2.1请求体长什么样 A

client.py
messages = [
    {"role": "system", "content": "你是学习教练，回答简短。"},
    {"role": "user", "content": "我每天学习时长多少合适？"},
]
payload = {"model": "mock", "messages": messages}

三件事和阶段二不同：多了 model 字段；问题包在 messages 里；多了一个 system 角色来定风格。

2.2响应与用量 A

client.py（解析）
payload = json.loads(response.read())
reply = payload["choices"][0]["message"]["content"]
usage = payload["usage"]
print("回复：", reply)
print("用量：", usage)
模拟服务返回（用量是写死的假数据）
回复： 建议每天 40 分钟。
用量： {'prompt_tokens': 18, 'completion_tokens': 9}

这里的 18 和 9 是本机模拟服务写死的数字，只用来演示格式。真实接口的 usage 来自响应体，由服务商计算，不能拿来对账以外的用途。

prompt_tokens 是你送进去的长度，completion_tokens 是它写出来的长度。两者都计费，所以长 system 提示、长对话历史都会让成本上涨。

词人话
messages带角色的对话记录，模型按顺序读
rolesystem 定规矩、user 提问题、assistant 是模型的话
choices[0]通常只有一个候选回答，取第一个
usage这次调用的 token 用量
两个坑。把历史对话全塞进去，token 会越滚越大；system 写成一大段规则，每次调用都要重复付钱。

2. 为什么长对话会让成本上升？

3. 从响应里取回答，为什么要经过 choices[0].message.content？

Chapter 3

记忆：把对话存进数据库

学完能做出：把每一轮对话写进 SQLite，程序重启后还能接着聊。

Agent 要有“上次说到哪”的能力。变量只活到程序结束，数据库能活到下次启动。

打个比方。看病时的病历本。医生不会每次都问一遍“你对什么过敏”，他翻本子。
对话表就是病历本：一行一句，带角色和时间，下次接着往后写。

3.1建表并写入 A

memory.py
import sqlite3
from pathlib import Path

db_path = Path("memory.db")
db_path.unlink(missing_ok=True)
db = sqlite3.connect(db_path)
db.execute("""CREATE TABLE messages (
    id INTEGER PRIMARY KEY,
    role TEXT NOT NULL,
    content TEXT NOT NULL,
    created_at TEXT DEFAULT CURRENT_TIMESTAMP
)""")

db.execute("INSERT INTO messages(role, content) VALUES (?, ?)", ("user", "我每天该学多久？"))
db.execute("INSERT INTO messages(role, content) VALUES (?, ?)", ("assistant", "建议每天 40 分钟。"))
db.execute("INSERT INTO messages(role, content) VALUES (?, ?)", ("user", "那算法练多久？"))
db.commit()

每一行是一条消息，顺序靠 id。下次要接着聊，就读出来拼成 messages 列表再发给模型。

3.2读回来 A

memory.py（读取）
rows = db.execute("SELECT id, role, content FROM messages ORDER BY id").fetchall()
for row in rows:
    print(row)
print("条数：", len(rows))
实际输出
(1, 'user', '我每天该学多久？')
(2, 'assistant', '建议每天 40 分钟。')
(3, 'user', '那算法练多久？')
条数： 3

3.3别让病历本无限变厚 B

历史越长，token 越贵。做法：只取最近 N 轮；或者把更早的对话压成一段摘要再带上。两种都要在配置文件里写明 N 是多少。

词人话
会话记忆按顺序存下来的对话
ORDER BY id按写入顺序读，保证对话不倒叙
窗口只带最近几条，控制长度和成本
摘要把旧对话压成一句，代替原文
两个坑。只存不读，等于没记忆；把全部历史每次都发一遍，账单会随对话长度线性上涨。

自测三问：

1. 为什么记忆不能放普通变量？

2. ORDER BY id 少了会怎样？

3. 历史太长有哪两种处理办法？

Chapter 4

检索：先找资料再回答

学完能做出：从本地笔记里找出最相关的三条，拼进提示再交给模型。

模型不知道你自己的笔记。硬把它塞进 prompt 又太长，所以先检索，再回答。

打个比方。考试允许带书。聪明人不会把整本书摊开，而是先按目录找到那一页，再照着回答。
检索就是“按目录找页”：把每条笔记变成一串数，把问题也变成一串数，谁的数字最接近就翻哪一页。

4.1把笔记变成向量 A

这里用最笨但看得懂的办法：数关键词出现了几次。真实系统用模型给的向量，原理一样。

retrieval.py
KEYWORDS = ["算法", "结构", "线程", "文件", "数据库", "Agent", "模型", "日志", "上限", "重试"]

NOTES = [
    "二分查找每次砍掉一半，属于算法。",
    "哈希表用空间换时间，属于数据结构。",
    "线程共享数据要加锁，否则会丢更新。",
    "文件读写要指定编码，路径要用脚本位置。",
    "SQL 参数化能防注入，事务保证要么全成要么全回滚。",
    "Agent 要有步数上限和日志，模型调用要处理超时。",
    "循环没有上限会一直调用模型，必须设最大步数。",
    "工具失败就重试一次，两次都失败就记 error。",
]

def vector(text):
    return [text.count(word) for word in KEYWORDS]

4.2谁最接近 A

retrieval.py（排序）
query = "Agent 为什么要设步数上限？"
qv = vector(query)
scores = [(cosine(qv, vector(note)), note) for note in NOTES]
scores.sort(reverse=True)
for score, note in scores[:3]:
    print(f"{score:.3f}  {note}")
实际输出
0.707  Agent 要有步数上限和日志，模型调用要处理超时。
0.500  循环没有上限会一直调用模型，必须设最大步数。
0.000  线程共享数据要加锁，否则会丢更新。

第一名和第二名都和“上限”有关，第三名完全无关（得分 0）。取前两名就够了，把整本笔记塞进去既贵又吵。

4.3拼进提示 B

retrieval.py（拼接）
context = "\n".join(note for score, note in scores[:2] if score > 0)
prompt = f"只根据下面的资料回答：\n{context}\n\n问题：{query}"

“只根据下面的资料回答”这句很关键，否则模型会用自己的知识补充，你就没法判断答案是从笔记来的还是编的。

4.4真实检索的三步 B

关键词计数只能做演示。真实检索要先做三件事，缺一件效果就掉：

步骤做什么常见参数不做的后果
分块把长文档切成 200–500 字的片段，相邻块留一点重叠重叠 10%–20%整篇塞进向量，检索粒度太粗，答非所问
向量化用 embedding 模型把每块变成向量，存起来768 / 1536 维用关键词计数，同义改写就召不回来
评估准备“问题 → 正确片段”的对照表，算 recall@kk 取 3–5不知道检索好不好，只能感觉“好像还行”

recall@k 的意思：在 k 条召回结果里，有没有包含那条正确片段。10 个问题里 8 个命中，就是 80%。这个数字比“看起来相关”可靠。

常见误判。检索命中但模型答错，是生成的问题；检索没命中却答对，是模型在编。两种情况要分开统计，否则永远不知道该改哪一段。
词人话
检索先从自己的资料里找相关段落
向量化把文字变成一串能比较的数
Top-K只取最相关的 K 条
上下文拼进提示的那几段资料
两个坑。把得分 0 的笔记也拼进去，等于给模型添乱；不写“只根据资料回答”，模型会自由发挥，答案无法追溯。

自测三问：

1. 为什么不能把所有笔记直接拼进提示？

2. 得分 0 代表什么？

3. “只根据下面的资料回答”这句话防的是什么？

Chapter 5

循环控制：上限与重复检测

学完能做出：一个会自己停下的循环，卡住时能识别并退出。

阶段二的循环只有步数上限。真实情况更糟：工具一直失败，模型就会一直重试同一个动作，五步全浪费。

打个比方。遛狗要牵绳。绳子长度是最大步数；狗原地转圈时，你得把它拽回来——这就是重复检测。
没有绳子，它能跑到明天；没有重复检测，它能在原地转到你破产。

5.1先看卡住的样子 A

loop.py
def get_weather(args):
    return {"ok": False, "error": "service timeout"}

def decide(state, history):
    if state["rain"] is None:
        return "get_weather", {"city": "常州"}
    return "finish", {}

state = {"rain": None}
history = []
for step in range(1, 6):
    action, args = decide(state, history)
    if action == "finish":
        print(f"[{step}] 结束")
        break
    if history.count(action) >= 2:
        print(f"[{step}] 检测到动作 {action} 重复两次，停止")
        break
    result = get_weather(args)
    history.append(action)
    print(f"[{step}] {action} → {result}")
实际输出
[1] get_weather → {'ok': False, 'error': 'service timeout'}
[2] get_weather → {'ok': False, 'error': 'service timeout'}
[3] 检测到动作 get_weather 重复两次，停止

第三轮本来还会再调一次。重复检测在它动手之前就拦住了，省下后面两步和对应的 token。

5.2三层刹车 A

刹车什么时候用触发后做什么
最大步数永远开着直接停，返回“未完成”
重复检测同一个动作连续两次停，并说明卡在哪
超时预算对外部接口单次调用就别等太久

三种都要有。只有最大步数，会白白烧掉五步；只有重复检测，遇到“每次换个工具但都不成功”还是停不下来。

两个坑。重复检测看“动作名”，如果参数每次都变（比如时间戳），就检测不到；停下时要说清原因，否则你以为是任务完成了。

自测三问：

1. 最大步数和重复检测各防什么？

2. 为什么停下时要带原因？

3. 什么情况下重复检测会失灵？

Chapter 6

评测：通过率与失败清单

学完能做出：一套固定的 Agent 测试，报出通过率和每一条失败原因。

改一处代码，你不知道有没有弄坏别的。没有评测，只能靠手点，点三次就烦了。

打个比方。体检。项目固定（血压、血糖、心电图），每次结果能对比；
如果每次体检项目都不一样，你无法判断“这次是好还是坏”。评测就是给 Agent 做体检。

for goal, must in CASES:

    if must in reply:

Chapter 7

交付：一条命令跑完

学完能做出：python agent.py --goal "..." 一条命令跑出结果，并把过程写进日志。

前面七章都是零件。这一章把它们装进一个入口，让使用者只需要记住一条命令。

打个比方。餐厅后厨可以很复杂，但客人只需要“点菜”一个动作。
入口脚本就是出餐口：参数从菜单来，过程在后厨，端出来的只有结果和一张小票（日志）。

7.1接参数 A

agent.py（节选：只列入口部分）
import argparse, json, logging
from pathlib import Path

ROOT = Path(__file__).parent
CONFIG = json.loads((ROOT / "config.json").read_text(encoding="utf-8"))
logging.basicConfig(filename=ROOT / "agent.log", level=logging.INFO,
                    format="%(asctime)s %(levelname)s %(message)s", encoding="utf-8")

parser = argparse.ArgumentParser()
parser.add_argument("--goal", default="明天要不要带伞")
args = parser.parse_args()
print("目标：", args.goal)
print("答案：", run(args.goal))
实际输出
目标： 明天要不要带伞
[1] get_weather → {'city': '常州', 'rain': True}
[2] 结论：带伞
答案： 带伞

7.2交付前检查表 A

项过了的标志
一条命令能跑不带参数也有默认目标，报错时给用法
参数在配置里换城市、换地址不用改代码
日志落盘agent.log 能看到每一步
失败有交代工具挂了会重试，再失败就明确报错
评测可复跑evaluate.py 结果稳定，能对比版本
说明书README 里两条命令能跑通
两个坑。只在你的机器上能跑（路径写死、依赖没写进 requirements）；把 agent.log 和 agent.db 提交进仓库，越跑越大。

Appendix

附录：工程检查表、术语、下一步

A.1工程检查表

  • 可调参数全部在 config.json，代码里没有魔法数字。
  • 每一步都有日志，日志带时间和步骤号。
  • 工具返回值统一成字典，成功失败结构一致。
  • 外部调用有重试上限，且只重试幂等操作。
  • 循环有最大步数、重复检测、超时预算。
  • 对话历史落库，且有长度上限。
  • 评测集固定，结果可复跑，失败原因写清楚。
  • 一条命令能跑，README 两条命令能复现。

A.2术语表

词一句话
配置外置会变的值不写在代码里
结构化日志带时间、级别、步骤号的记录
幂等同一个请求做两遍，结果一样
重试上限失败最多再试几次，超过就报错
上下文窗口这次送给模型的历史和资料总量
RAG先检索自己的资料，再让模型回答
重复检测同一动作连续出现就停
回归测试改完一处，确认别处没坏
可复现别人按说明书能跑出同样结果
