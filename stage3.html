Chapter 0

从脚本到工程：配置、日志、入口

学完能做出：一个带配置文件、会写日志、有明确入口的程序骨架。

阶段二的代码，参数都写死在函数里。改个城市要改代码，出了错没有任何记录。这一章先解决这两件事。

打个比方。开一家小店，三样东西缺一不可：菜单（客人能选什么，你不用每次口头解释）、账本（谁来过、点了什么、出了什么问题）、店门（客人从哪进来）。
配置文件是菜单，日志是账本，入口脚本是店门。没有它们，那不叫店，叫你自己在家做饭。

0.1菜单：config.json A

config.json
{
  "city": "常州",
  "max_steps": 5,
  "retry_limit": 2,
  "model_url": "http://127.0.0.1:18090/chat"
}

四个值都是“会变但不想改代码”的东西。改城市、改步数上限、换模型地址，只动这一个文件。

0.2账本：日志 A

config_and_log.py
import json, logging                          # 读 JSON、写日志
from pathlib import Path                      # 处理文件路径

ROOT = Path(__file__).parent                  # 本文件所在的目录
CONFIG = json.loads((ROOT / "config.json").read_text(encoding="utf-8"))  # 读配置文件，转成字典

logging.basicConfig(
    level=logging.INFO,                        # 记录 INFO 及以上的日志
    format="%(asctime)s %(levelname)s %(message)s",  # 时间、级别、内容
    handlers=[logging.FileHandler(ROOT / "agent.log", encoding="utf-8")],  # 写进文件，UTF-8 防乱码
)
log = logging.getLogger("agent")               # 拿到一个叫 agent 的记录器

log.info("启动，城市=%s，最多 %d 步", CONFIG["city"], CONFIG["max_steps"])  # %s 填字符串，%d 填整数
print("配置：", CONFIG)                          # 同时打印一份到屏幕

配置这四个键各管一件事，改值不用改代码：

键谁用它改了会怎样
city天气工具查的城市跟着变
max_steps循环最多允许走几步就停
retry_limit工具调用层失败后再试几次
model_url模型客户端请求发到哪个地址
实际输出
配置： {'city': '常州', 'max_steps': 5, 'retry_limit': 2, 'model_url': 'http://127.0.0.1:18090/chat'}
2026-11-06 10:22:34,185 INFO 启动，城市=常州，最多 5 步

日志和 print 的区别：print 给人看，日志给“出问题时的你”看。它带时间、带级别，还能只写进文件不刷屏。

词人话
配置会变的值，放在代码外面
日志级别INFO 正常、WARNING 要留意、ERROR 出问题了
%s / %d占位符：字符串、整数，日志模块替你填
Path(__file__).parent脚本自己所在的目录，不受启动位置影响
两个坑。配置文件用相对路径 "config.json"，从别的目录启动就找不到；日志文件不写 encoding="utf-8"，中文会乱码。

Chapter 1

工具层：签名、校验、重试

学完能做出：一个失败会自动重试、失败两次就如实报错的工具调用层。

真实工具会超时、会返回奇怪的参数、会突然挂掉。工具层就是给这些意外加一层缓冲。

打个比方。插头要有统一的规格（参数校验），不然插不进去；跳闸了要能自动合闸（重试），合两次还跳，就得停电检修（报错），不能一直合闸把线路烧了。

1.1先看失败长什么样 A

tools.py
CALLS = {"n": 0}                                  # 计数器：记录这个工具被调了几次

def flaky_weather(args):                          # 定义工具；args 是参数字典
    CALLS["n"] += 1                               # 每调用一次，计数加一
    if CALLS["n"] < 3:                            # 前两次（第 1、2 次）
        raise TimeoutError("weather service timeout")  # 主动抛超时错误，模拟服务挂掉
    return {"city": args["city"], "rain": True}   # 第三次成功：返回城市和是否下雨

TOOLS = {"flaky_weather": flaky_weather}          # 工具表：名字 → 函数，call_tool 靠它找函数

这个工具前两次必失败，第三次成功。用它才能验证重试是真的有用。

1.2重试不是循环重发 A

tools.py（调用层）
def call_tool(name, args, retry_limit=2):          # name 工具名，args 参数，retry_limit 重试上限
    for attempt in range(1, retry_limit + 2):      # 首次 + 2 次重试 = 一共 3 次机会
        try:                                       # 尝试执行
            result = TOOLS[name](args)             # 从工具表里按名字取函数并调用
            return {"ok": True, "result": result, "attempts": attempt}  # 成功：带上第几次成功
        except Exception as error:                 # 捕获任何异常
            print(f"  第 {attempt} 次失败：{type(error).__name__}: {error}")  # 打印错误类型和内容
            if attempt > retry_limit:               # 已经用满重试次数
                return {"ok": False, "error": str(error), "attempts": attempt}  # 如实返回失败
实际输出
  第 1 次失败：TimeoutError: weather service timeout
  第 2 次失败：TimeoutError: weather service timeout
{'ok': True, 'result': {'city': '常州', 'rain': True}, 'attempts': 3}

三个要点：返回值永远是一个字典（成功失败结构一致）；记下第几次才成功；超过上限就停下，不无限重试。

flowchart TD
    A["调用工具"] --> B{"成功？"}
    B -->|"是"| C["返回 ok 与结果"]
    B -->|"否"| D{"还有重试次数？"}
    D -->|"有"| E["等一会儿再试"]
    E --> A
    D -->|"没有"| F["返回 error 与原因"]

看图要点：只有“没到上限”才回到调用，到了上限就如实报错，不再绕圈。

1.3参数校验放在工具入口 B

模型可能传错东西：把城市传成数字、少传字段。校验放在工具内部，用一句明确的话拒绝，比在后面崩掉好排查。

tools.py（校验）
def get_weather(args):                             # 工具入口，参数是字典
    city = args.get("city")                        # 取城市；没有这个键就得到 None
    if not isinstance(city, str) or not city:      # 不是字符串，或者是空字符串
        raise ValueError("city 必须是非空字符串")    # 明确拒绝，别往下走
    return {"city": city, "rain": True}            # 校验通过，返回结果
词人话
重试次数“再多试几次”，不含第一次
幂等同一个请求做两遍，结果一样；只有幂等的工具才适合自动重试
返回值统一成功失败都是字典，调用方不用猜
校验进门先查证件，别等用到一半才崩
两个坑。把“发消息”“下单”这类工具自动重试，可能发两遍；重试之间没有等待，对方可能还没恢复。

Chapter 2

接模型：messages 协议与用量

学完能做出：用主流消息格式调用模型，并读出这次花了多少 token。

阶段二用的是自定义的 {"prompt": ...}。真实接口不是这样，它要一串“谁说了什么”。

打个比方。你跟客服聊天，系统会显示“客服：您好”“你：我想退货”“客服：请提供订单号”。
模型收到的也是这种带角色的对话记录，不是一句孤立的问题。角色只有三种：system（规定它怎么说话）、user（你说的）、assistant（它说的）。

2.1请求体长什么样 A

client.py
messages = [                                    # 一串消息，按顺序交给模型
    {"role": "system", "content": "你是学习教练，回答简短。"},  # 规定它的身份和说话风格
    {"role": "user", "content": "我每天学习时长多少合适？"},    # 你这次问的问题
]
payload = {"model": "mock", "messages": messages}  # 请求体：用哪个模型 + 带上消息

三件事和阶段二不同：多了 model 字段；问题包在 messages 里；多了一个 system 角色来定风格。

2.2响应与用量 A

client.py（解析）
import json, urllib.request                     # JSON、HTTP 客户端
request = urllib.request.Request("http://127.0.0.1:18090/chat",  # 模拟模型地址
                                 data=json.dumps(payload).encode("utf-8"),  # 请求体：上一段拼好的 messages
                                 headers={"Content-Type": "application/json"})  # 声明送的是 JSON
response = urllib.request.urlopen(request, timeout=3)  # 发出去，拿到响应
payload = json.loads(response.read())           # 把响应里的字节转成字典
reply = payload["choices"][0]["message"]["content"]  # 第一个候选回答的文字
usage = payload["usage"]                         # 这次调用的 token 用量
print("回复：", reply)                            # 打印回答
print("用量：", usage)                            # 打印用量
模拟服务返回（用量是写死的假数据）
回复： 建议每天 40 分钟。
用量： {'prompt_tokens': 18, 'completion_tokens': 9}

这里的 18 和 9 是本机模拟服务写死的数字，只用来演示格式。真实接口的 usage 来自响应体，由服务商计算，不能拿来对账以外的用途。

prompt_tokens 是你送进去的长度，completion_tokens 是它写出来的长度。两者都计费，所以长 system 提示、长对话历史都会让成本上涨。

词人话
messages带角色的对话记录，模型按顺序读
rolesystem 定规矩、user 提问题、assistant 是模型的话
choices[0]通常只有一个候选回答，取第一个
usage这次调用的 token 用量
两个坑。把历史对话全塞进去，token 会越滚越大；system 写成一大段规则，每次调用都要重复付钱。

2. 为什么长对话会让成本上升？

Chapter 3

记忆：把对话存进数据库

学完能做出：把每一轮对话写进 SQLite，程序重启后还能接着聊。

Agent 要有“上次说到哪”的能力。变量只活到程序结束，数据库能活到下次启动。

打个比方。看病时的病历本。医生不会每次都问一遍“你对什么过敏”，他翻本子。
对话表就是病历本：一行一句，带角色和时间，下次接着往后写。

3.1建表并写入 A

memory.py
import sqlite3                                  # Python 自带的数据库
from pathlib import Path                        # 处理文件路径

db_path = Path("memory.db")                     # 数据库文件放在当前目录
db_path.unlink(missing_ok=True)                 # 每次重跑先删掉旧库，从干净状态开始
db = sqlite3.connect(db_path)                   # 打开（或新建）数据库
db.execute("""CREATE TABLE messages (           # 建表：一行一条消息
    id INTEGER PRIMARY KEY,                     # 编号，自增，唯一
    role TEXT NOT NULL,                         # 谁说的：user / assistant
    content TEXT NOT NULL,                      # 说了什么
    created_at TEXT DEFAULT CURRENT_TIMESTAMP   # 写入时间，自动填
)""")

db.execute("INSERT INTO messages(role, content) VALUES (?, ?)", ("user", "我每天该学多久？"))      # 加一条用户消息
db.execute("INSERT INTO messages(role, content) VALUES (?, ?)", ("assistant", "建议每天 40 分钟。"))  # 加一条模型回复
db.execute("INSERT INTO messages(role, content) VALUES (?, ?)", ("user", "那算法练多久？"))          # 再加一条
db.commit()                                      # 提交，不提交等于没写

每一行是一条消息，顺序靠 id。下次要接着聊，就读出来拼成 messages 列表再发给模型。

3.2读回来 A

memory.py（读取）
rows = db.execute("SELECT id, role, content FROM messages ORDER BY id").fetchall()  # 按编号顺序取全部
for row in rows:                                # 一行一行处理
    print(row)                                  # 每行是 (编号, 角色, 内容)
print("条数：", len(rows))                       # 一共几条
实际输出
(1, 'user', '我每天该学多久？')
(2, 'assistant', '建议每天 40 分钟。')
(3, 'user', '那算法练多久？')
条数： 3

3.3别让病历本无限变厚 B

历史越长，token 越贵。做法：只取最近 N 轮；或者把更早的对话压成一段摘要再带上。两种都要在配置文件里写明 N 是多少。

词人话
会话记忆按顺序存下来的对话
ORDER BY id按写入顺序读，保证对话不倒叙
窗口只带最近几条，控制长度和成本
摘要把旧对话压成一句，代替原文
两个坑。只存不读，等于没记忆；把全部历史每次都发一遍，账单会随对话长度线性上涨。

1. 为什么记忆不能放普通变量？

2. ORDER BY id 少了会怎样？

3. 历史太长有哪两种处理办法？

Chapter 4

检索：先找资料再回答

学完能做出：从本地笔记里找出最相关的三条，拼进提示再交给模型。

模型不知道你自己的笔记。硬把它塞进 prompt 又太长，所以先检索，再回答。

打个比方。考试允许带书。聪明人不会把整本书摊开，而是先按目录找到那一页，再照着回答。
检索就是“按目录找页”：把每条笔记变成一串数，把问题也变成一串数，谁的数字最接近就翻哪一页。

4.1把笔记变成向量 A

这里用最笨但看得懂的办法：数关键词出现了几次。真实系统用模型给的向量，原理一样。

retrieval.py
import math                                      # 算平方根，后面 cosine 用

KEYWORDS = ["算法", "结构", "线程", "文件", "数据库", "Agent", "模型", "日志", "上限", "重试"]  # 词表：向量的每一位对应一个词

NOTES = [                                       # 你的资料库，每行是一条笔记
    "二分查找每次砍掉一半，属于算法。",
    "哈希表用空间换时间，属于数据结构。",
    "线程共享数据要加锁，否则会丢更新。",
    "文件读写要指定编码，路径要用脚本位置。",
    "SQL 参数化能防注入，事务保证要么全成要么全回滚。",
    "Agent 要有步数上限和日志，模型调用要处理超时。",
    "循环没有上限会一直调用模型，必须设最大步数。",
    "工具失败就重试一次，两次都失败就记 error。",
]

def vector(text):                               # 把一段文字变成向量
    return [text.count(word) for word in KEYWORDS]  # 每个词出现几次，就是这一位的值

def cosine(a, b):                               # 两支向量的方向相似度
    dot = sum(x * y for x, y in zip(a, b))       # 对应位相乘再相加（点积）
    na = math.sqrt(sum(x * x for x in a))        # a 的长度
    nb = math.sqrt(sum(y * y for y in b))        # b 的长度
    return dot / (na * nb) if na and nb else 0.0  # 点积 ÷ 两长度；全零向量记 0 分

4.2谁最接近 A

retrieval.py（排序）
query = "Agent 为什么要设步数上限？"              # 用户的问题
qv = vector(query)                              # 问题也变成向量
scores = [(cosine(qv, vector(note)), note) for note in NOTES]  # 每条笔记算一个相似度，配成 (分数, 原文)
scores.sort(reverse=True)                       # 按分数从高到低排
for score, note in scores[:3]:                  # 只看前三名
    print(f"{score:.3f}  {note}")                # 保留三位小数，连同原文打印
实际输出
0.707  Agent 要有步数上限和日志，模型调用要处理超时。
0.500  循环没有上限会一直调用模型，必须设最大步数。
0.000  线程共享数据要加锁，否则会丢更新。

第一名和第二名都和“上限”有关，第三名完全无关（得分 0）。取前两名就够了，把整本笔记塞进去既贵又吵。

4.3拼进提示 B

retrieval.py（拼接）
context = "\n".join(note for score, note in scores[:2] if score > 0)  # 取前二，丢掉 0 分，用换行拼起来
prompt = f"只根据下面的资料回答：\n{context}\n\n问题：{query}"          # 规定答题依据，再放资料和问题

“只根据下面的资料回答”这句很关键，否则模型会用自己的知识补充，你就没法判断答案是从笔记来的还是编的。

4.4真实检索的三步 B

关键词计数只能做演示。真实检索要先做三件事，缺一件效果就掉：

步骤做什么常见参数不做的后果
分块把长文档切成 200–500 字的片段，相邻块留一点重叠重叠 10%–20%整篇塞进向量，检索粒度太粗，答非所问
向量化用 embedding 模型把每块变成向量，存起来768 / 1536 维用关键词计数，同义改写就召不回来
评估准备“问题 → 正确片段”的对照表，算 recall@kk 取 3–5不知道检索好不好，只能感觉“好像还行”

recall@k 的意思：在 k 条召回结果里，有没有包含那条正确片段。10 个问题里 8 个命中，就是 80%。这个数字比“看起来相关”可靠。

常见误判。检索命中但模型答错，是生成的问题；检索没命中却答对，是模型在编。两种情况要分开统计，否则永远不知道该改哪一段。
词人话
检索先从自己的资料里找相关段落
向量化把文字变成一串能比较的数
Top-K只取最相关的 K 条
上下文拼进提示的那几段资料
两个坑。把得分 0 的笔记也拼进去，等于给模型添乱；不写“只根据资料回答”，模型会自由发挥，答案无法追溯。

自测三问：

1. 为什么不能把所有笔记直接拼进提示？

2. 得分 0 代表什么？

3. “只根据下面的资料回答”这句话防的是什么？

Chapter 5

循环控制：上限与重复检测

学完能做出：一个会自己停下的循环，卡住时能识别并退出。

阶段二的循环只有步数上限。真实情况更糟：工具一直失败，模型就会一直重试同一个动作，五步全浪费。

打个比方。遛狗要牵绳。绳子长度是最大步数；狗原地转圈时，你得把它拽回来——这就是重复检测。
没有绳子，它能跑到明天；没有重复检测，它能在原地转到你破产。

5.1先看卡住的样子 A

loop.py
def get_weather(args):                          # 天气工具（这里故意失败）
    return {"ok": False, "error": "service timeout"}  # 返回失败，模拟服务超时

def decide(state, history):                     # 决定下一步干什么
    if state["rain"] is None:                   # 还没查到天气
        return "get_weather", {"city": "常州"}    # 那就先调天气工具
    return "finish", {}                         # 查到了就结束

state = {"rain": None}                          # 状态：天气还不知道
history = []                                    # 记录做过的动作
for step in range(1, 6):                        # 最多走 5 步
    action, args = decide(state, history)       # 问：下一步做什么
    if action == "finish":                      # 该结束了
        print(f"[{step}] 结束")
        break
    if history.count(action) >= 2:              # 同一个动作已经做过两次
        print(f"[{step}] 检测到动作 {action} 重复两次，停止")  # 拦住，不再调
        break
    result = get_weather(args)                  # 执行工具
    history.append(action)                      # 记进历史
    print(f"[{step}] {action} → {result}")      # 打印这一步的结果
实际输出
[1] get_weather → {'ok': False, 'error': 'service timeout'}
[2] get_weather → {'ok': False, 'error': 'service timeout'}
[3] 检测到动作 get_weather 重复两次，停止

第三轮本来还会再调一次。重复检测在它动手之前就拦住了，省下后面两步和对应的 token。

5.2三层刹车 A

刹车什么时候用触发后做什么
最大步数永远开着直接停，返回“未完成”
重复检测同一个动作连续两次停，并说明卡在哪
超时预算对外部接口单次调用就别等太久

三种都要有。只有最大步数，会白白烧掉五步；只有重复检测，遇到“每次换个工具但都不成功”还是停不下来。

两个坑。重复检测看“动作名”，如果参数每次都变（比如时间戳），就检测不到；停下时要说清原因，否则你以为是任务完成了。

CASES = [                                       # 卷子：每条是（问题，必须出现的关键词）
    ("明天要带伞吗？", "带伞"),
    ("我每天学多久？", "40 分钟"),
    ("算法怎么练？", "先做题"),
    ("怎么复习？", "错题"),
    ("数据存在哪？", "SQLite"),
    ("为什么要日志？", "排查"),
    ("Agent 要限制什么？", "步数"),
    ("接口超时怎么办？", "重试"),
]

ANSWERS = {                                      # 假 Agent 的回答表：问题 → 回答
    "明天要带伞吗？": "有雨，带伞。", "我每天学多久？": "每天 40 分钟。",
    "算法怎么练？": "先做题再看讲解。", "怎么复习？": "每天回顾错题。",
    "数据存在哪？": "存进 SQLite。", "为什么要日志？": "出问题能排查。",
    "Agent 要限制什么？": "限制步数和重试次数。", "接口超时怎么办？": "等一会儿再问一次。",
}

def run_agent(goal):                             # 按问题查表，查不到就说不知道
    return ANSWERS.get(goal, "不知道")

passed, failed = 0, []                           # 计分器：通过数、失败清单

for goal, must in CASES:                        # 一条一条考
    reply = run_agent(goal)                     # 让 Agent 回答
    if must in reply:                           # 回答里出现了关键词
        passed += 1                             # 算通过
    else:
        failed.append((goal, must, reply))      # 记下问题、期望、实际回答

评分标准怎么算“对”：关键词、完全匹配、人工判定
两个坑。只报通过率不报失败原因，你不知道该改哪；评分标准太严，正确回答也会被判错。
